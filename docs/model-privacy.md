# Фильтр отправляемых данных (FIN-366)

Фильтр работает в `aistudio.Client.StreamGuarded` перед проверкой бюджета, чтением ключа и каждым HTTP POST. Он обрабатывает отправляемую копию, включая `Stream`, которым пользуются транспортные тесты. Исходные вопросы, история, операции, trusted facts presenter и файлы не изменяются. Сбой разбора, неоднозначный JSON, непустой encrypted_content или превышение глубины 64 завершают генерацию штатным `MODEL_ERROR` с возвратом попытки; исходный запрос в обход фильтра не отправляется.

## Проверенный состав входа

Аудит прослеживает `generation.Engine.execute` → `GenerationModel.Stream` → `Client.StreamGuarded` и `FinancialData.result/modelFacts`. Примеры синтетические. Отдельные поля ФИО владельца/получателя, телефона, email и полного номера счёта в текущих пяти ответах финансовых RPC отсутствуют; свободные имена могут находиться в описаниях и подписях. Полные исходные OFX и профиль пользователя модель не получает. Отдельный opt-in `scripts/record-aistudio.py` — диагностический recorder с фиксированными синтетическими вопросами/результатами, без входа пользовательских диалогов; рабочая серверная генерация через него не проходит. Его прямые synthetic-only HTTP-пробы не являются обходным путём обработки запросов приложения.

| Источник / поле | Нужен для ответа; правило отправляемой копии | Пример и ограничения |
|---|---|---|
| Текущий `GenerationTask.Text`, вопросы/ответы завершённых пар истории | Текст нужен; поддерживаемые реквизиты заменяются | `телефон +7 (999) 123-45-67` → `телефон [phone_<код>]`; имя внутри свободного текста сохраняется |
| Overview: диапазоны, полнота, доступные поля, названия источников | Сохраняются; тексты проходят общий фильтр | Т-Банк, даты и число полных месяцев сохраняются |
| Aggregate: totals, groups, merchant.title, filters | Суммы, группы и selection-токены нужны; текстовые подписи/поисковый q проходят фильтр | Разные merchant.selection сохраняют разные группы даже при совпадении имён; фильтр их не объединяет |
| Find: Operation.id | UUID не нужен: presenter выбирает результат по call_id/позиции; исключается до protojson | Поле `id` операции отсутствует только в JSON модели |
| Find: account/from_account/to_account | type_name и mask сохраняются для различения; spoken исключается как дубль для озвучивания интерфейса | `Текущий ··4821` сохраняется; это не полное обезличивание счёта |
| Find: title, description, note/details, bank_category, source_name | Не удаляются целиком; проходят текстовые правила | Название аптеки, имя в описании и финансовая часть сохраняются; распознавания имён нет |
| Analytics / ListPeriods: блоки и произвольный Struct data | Нужные блоки/числа/периоды сохраняются, JSON обходится рекурсивно | Числа и protobuf int64 в строках не проходят float64; label с email маскируется |
| Приватные source revisions | Уже исключались из JSON модели FIN-368; trusted Evidence остаётся | Ревизии продолжают подтверждать точные исходные snapshots |
| `function_call_output.output`, `function_call.arguments` | JSON внутри строк разбирается и фильтруется повторно | `output` с описанием `card: 4111111111111111` не сохраняет исходный номер внутри escaped JSON |
| Provider messages, web_search_call, annotations и неизвестные текстовые поля известных items | Полная continuation перед каждым следующим POST фильтруется заново | Сохраняются call_id и обычные citation URL; необычные кодировки значений ограничены правилами ниже |
| Provider reasoning / encrypted_content | Видимые reasoning items сохраняются и фильтруются; непустой encrypted_content запрещает следующий POST целиком | Непрозрачный payload нельзя проверить; отсутствие/пустой encrypted_content допустимо, но не заменяется удалением необходимого контекста |
| Server instructions и tools | Также проходят фильтр; tools, включая встроенный web_search, сохраняются | Новых смысловых запретов или словаря запрещённых вопросов нет |

## Поддерживаемые форматы

- Email: обычный local-part `name+tag@example.test`, включая буквенные Unicode local-part/домены. Замена сохраняет различие исходных значений.
- Российский телефон: `+7` и 10 цифр; `7`/`8` и 10 цифр с обычными пробелами, NBSP/узким NBSP, скобками и дефисами. Неформатированные `7/8XXXXXXXXXX` распознаются после `телефон`, `тел`, `phone`, `mobile`. Границы соседних цифр проверяются; `8…` нормализуется к `7…` для одного псевдонима.
- Карта: 13–19 непрерывных цифр после `карта/карты/карте/карту/картой/картою/card/pan`. Форматированные группы по четыре цифры (всего 13–19), либо 4–6–5 для AmEx, распознаются при корректной контрольной сумме Луна. Группирование и контрольная сумма защищают обычные длинные суммы; голая числовая строка без контекста не считается картой.
- Счёт: 20 непрерывных цифр после `счёт/счет/счёта/счета`, `р/с`, `л/с`, `account`, `iban`; либо разделённый точками/пробелами/дефисами формат 5–3–1–4–7. Для российского счёта checksum без БИК не вычисляется. Полные IBAN иностранных форматов и произвольные международные телефоны этим набором не покрыты.

Псевдоним содержит тип и HMAC-SHA256, усечённый до 96 бит. Случайный ключ живёт только в памяти transport, область — ID конкретной генерации (сам ID не отправляется). В одном ответе одинаковый реквизит получает одинаковый код во всех вопросах, истории и результатах; разные значения — разные коды. Новая попытка `RetryAnswer` имеет другую область. В базе таблица соответствия не создаётся; исходные реквизиты остаются только в текущих локальных данных.

Чтобы сохранить поиск по описанию, адаптер восстанавливает известный псевдоним только в `filter.q` локальных `find_operations` и `aggregate_operations` перед обычной валидацией и выполнением. Например, модель возвращает `q: "[phone_<код>]"`, сервис ищет по исходному телефону. Остальные поля и инструменты, включая встроенный поиск, не получают обратную подстановку. Аргументы и их локальная raw-форма остаются согласованы; перед следующим HTTP они снова маскируются. Полный исходный/псевдонимизированный запрос и таблица соответствий не логируются.

## История, старый контекст и внедрение

Каждый POST строит полный вход из хранимых пар, текущего вопроса и локальной continuation. `store:false`, `x-data-logging-enabled:false`, отсутствие conversation/previous_response_id сохраняются. Поэтому после включения фильтра старая история заново проходит правила, а прежний контекст у провайдера не используется для продолжения. Отдельного обновления или переписывания сохранённой истории не требуется. Видимый provider reasoning фильтруется вместе с остальным контекстом. Непустой encrypted_content завершает продолжение ошибкой без следующего HTTP. На mixed-version развёртывании старый экземпляр ещё может отправлять без фильтра: для включения защиты необходимо обновить все экземпляры, обслуживающие генерацию. Уже совершённые внешние передачи эта правка не отменяет и не удаляет.

Перед включением нужна публикация владельцем окончательного юридического пакета FIN-141 с новой версией и URL согласия помощнику. Новая `current_version` включается через существующую consent gate сервиса user: ранее выданное согласие на старую версию не должно пропускать запросы к модели. Затем все экземпляры generation должны работать с новым фильтром, а Android — показывать исправленное раскрытие ([отдельная часть FIN-366](https://github.com/fin-assist/android/pull/204)). Это порядок внедрения, а не подтверждение состоявшейся публикации/выкладки. Фиктивное изменение версии mock-согласия датой публикацию не заменяет; новых контрактных полей не требуется.

## Reasoning и совместимость поставщика

В [официальной схеме Responses API](https://aistudio.yandex.ru/en/docs/ai-studio/api/Responses/createResponse) ReasoningItem должен включаться в следующий ручной контекст. Поэтому видимые summary/content и сам item сохраняются и проходят рекурсивный фильтр. Непустой encrypted_content не является проверяемым текстом: даже при наличии видимого summary вся следующая отправка прекращается с MODEL_ERROR/refund. Пустое значение/отсутствие допускается. Фильтр не объявляет summary расшифровкой ciphertext и не повторяет запрос без обязательного контекста.

Нынешние двенадцать реальных recordings Alice AI LLM Flash не содержат output reasoning items; их успешный offline replay не доказывает совместимость encrypted reasoning. Поставщик/модель, требующие encrypted context, этим начальным фильтром не поддерживаются. Новых платных запросов для проверки не делалось; произвольные модели и этот режим совместимостью не объявляются.

## Границы результата

Суммы, даты, валюты, остатки, категории, банковские и торговые названия сохраняются. Вопросы про аптеку, лекарства и здоровье не блокируются по словам; встроенный поиск сохраняется с прежними инструкциями. Отдельного посредника веб-поиска нет; фильтр HTTP-входа не является доказательством состава внутреннего поискового запроса поставщика.

Правила не распознают универсально ФИО, адреса, паспорта, специальные категории сведений, переписанные словами/Unicode-цифрами реквизиты, нестандартное группирование, обфускацию, percent/base64-кодирование или произвольные вложенные форматы. Голые длинные числа без указанного контекста сознательно сохраняются, чтобы не повреждать финансовые значения. Возможны ложные срабатывания на финансовый текст, который совпал с явно обозначенным реквизитом или форматом карты с валидной суммой Луна. Имя в свободном описании или чувствительный факт может остаться в запросе. Результат уменьшает избыточную передачу; он не гарантирует обнаружение всех ПДн, юридическое обезличивание или соблюдение всех требований закона.

Документы в Confluence, Политика и согласие помощнику синхронизируются в FIN-366 по этим фактическим ограничениям. Текст документов не должен обещать удаление всех имён/чувствительных фактов. Фильтр сам по себе не меняет порядок получения согласий или правовые основания обработки.

## Проверки

`privacy_test.go` проверяет поддерживаемые форматы, точность сумм/дат, разные значения и области, копирование, вложенный JSON, предел глубины, отказ до HTTP/ключа/резерва, HMAC-корреляцию и ограничение обратной подстановки. `privacy_integration_test.go` прогоняет настоящий Engine → HTTP → ответ функции → локальный финансовый поиск → второй HTTP с синтетической старой историей. `client/privacy_test.go` проверяет удаление UUID/а11y-дубля без изменения originals и настоящий gRPC. `app/privacy_api_test.go` вызывает AskQuestion/WatchAnswer/RetryAnswer через полную сборку с PostgreSQL 18 и проверяет фактические HTTP-запросы на каждом шаге, возврат попытки после HTTP-ошибки и неизменность сохранённого вопроса. Живые запросы в Yandex для этой проверки не нужны.
