# Фильтр отправляемых данных (FIN-366)

Фильтр работает в `aistudio.clientSession.streamGuarded` перед проверкой бюджета, чтением ключа и каждым HTTP POST. Он обрабатывает отправляемую копию, включая `Stream`, которым пользуются транспортные тесты. Исходные вопросы, история, операции, trusted facts presenter и файлы не изменяются. Сбой разбора, неоднозначный JSON, непустой encrypted_content или превышение глубины 64 завершают генерацию штатным `MODEL_ERROR` с возвратом попытки; исходный запрос в обход фильтра не отправляется.

## Проверенный состав входа

Аудит прослеживает `generation.Engine.execute` → `Model.NewSession` → `generationSession.Stream` → `clientSession.streamGuarded` и `FinancialData.result/modelFacts`. Примеры синтетические. Отдельные поля ФИО владельца/получателя, телефона, email и полного номера счёта в текущих пяти ответах финансовых RPC отсутствуют; свободные имена могут находиться в описаниях и подписях. Полные исходные OFX и профиль пользователя модель не получает. Отдельный opt-in `scripts/record-aistudio.py` — диагностический recorder с фиксированными синтетическими вопросами/результатами, без входа пользовательских диалогов; рабочая серверная генерация через него не проходит. Его прямые synthetic-only HTTP-пробы не являются обходным путём обработки запросов приложения.

| Источник / поле | Нужен для ответа; правило отправляемой копии | Пример и ограничения |
|---|---|---|
| Текущий `GenerationTask.Text`, вопросы/ответы завершённых пар истории | Текст нужен; поддерживаемые реквизиты заменяются | `телефон +7 (999) 123-45-67` → `телефон [phone_<код>]`; имя внутри свободного текста сохраняется |
| Overview: диапазоны, полнота, доступные поля, названия источников | Сохраняются; тексты проходят общий фильтр | Т-Банк, даты и число полных месяцев сохраняются |
| Aggregate: totals, groups, merchant.title, filters | Суммы, группы и selection-токены нужны; текстовые подписи/поисковый q проходят фильтр | Разные merchant.selection сохраняют разные группы даже при совпадении имён; фильтр их не объединяет |
| Find: Operation.id | UUID не нужен: presenter выбирает результат по call_id/позиции; исключается до protojson | Поле `id` операции отсутствует только в JSON модели |
| Find: account/from_account/to_account | type_name и mask сохраняются для различения; spoken исключается как дубль для озвучивания интерфейса | `Текущий ··4821` сохраняется; это не полное обезличивание счёта |
| Find: title, description, note/details, bank_category, source_name | Не удаляются целиком; проходят текстовые правила | Название аптеки, имя в описании и финансовая часть сохраняются; распознавания имён нет |
| Analytics / ListPeriods: блоки и произвольный Struct data | Нужные блоки/числа/периоды сохраняются, JSON обходится рекурсивно | Числа и protobuf int64 в строках не проходят float64; label с email маскируется |
| Приватные source revisions | Уже исключались из JSON модели FIN-368; trusted Evidence остаётся | Ревизии продолжают подтверждать точные исходные snapshots |
| `function_call_output.output`, `function_call.arguments` | JSON внутри строк разбирается и фильтруется повторно | `output` с описанием `card: 4111111111111111` не сохраняет исходный номер внутри escaped JSON |
| Provider messages, web_search_call, annotations и неизвестные текстовые поля известных items | Полная continuation перед каждым следующим POST фильтруется заново | Сохраняются call_id и обычные citation URL; необычные кодировки значений ограничены правилами ниже |
| Provider reasoning / encrypted_content | Видимые reasoning items сохраняются и фильтруются; непустой encrypted_content запрещает следующий POST целиком | Непрозрачный payload нельзя проверить; отсутствие/пустой encrypted_content допустимо, но не заменяется удалением необходимого контекста |
| Server instructions и tools | Также проходят фильтр; tools, включая встроенный web_search, сохраняются | Новых смысловых запретов или словаря запрещённых вопросов нет |

## Поддерживаемые форматы

- Email: обычный local-part `name+tag@example.test`, включая буквенные Unicode local-part/домены. Замена сохраняет различие исходных значений.
- Российский телефон: `+7` и 10 цифр; `7`/`8` и 10 цифр с обычными пробелами, NBSP/узким NBSP, скобками и дефисами. Неформатированные `7/8XXXXXXXXXX` распознаются после `телефон`, `тел`, `phone`, `mobile`. Границы соседних цифр проверяются; `8…` нормализуется к `7…` для одного псевдонима.
- Карта: 13–19 непрерывных цифр после `карта/карты/карте/карту/картой/картою/card/pan`. Форматированные группы по четыре цифры (всего 13–19), либо 4–6–5 для AmEx, распознаются при корректной контрольной сумме Луна. Проверяются окна целых групп с собственными границами: соседние `5000`, `100 рублей` и `1 октября` не поглощаются жадным совпадением в однозначных окнах. Группирование и контрольная сумма защищают обычные длинные суммы; неизвестная голая числовая строка без контекста не считается картой.
- Счёт: 20 непрерывных цифр после `счёт/счет/счёта/счета`, `р/с`, `л/с`, `account`, `iban`; либо разделённый точками/пробелами/дефисами формат 5–3–1–4–7. Для российского счёта checksum без БИК не вычисляется. Полные IBAN иностранных форматов и произвольные международные телефоны этим набором не покрыты.

Псевдоним содержит тип и HMAC-SHA256, усечённый до 96 бит. Случайный ключ живёт только в памяти transport, область задаёт случайный nonce отдельной сессии генерации; nonce не отправляется. Engine один раз вызывает typed `Model.NewSession` на весь execute: приватный словарь сохраняется между шагами, при отказе preflight и сокращении истории. Поэтому исчезновение первоначальной метки из истории не раскрывает восстановленный локальный q в следующем POST. Повторное сканирование не дублирует записи. Конкурентные генерации и новая попытка `RetryAnswer` имеют отдельные области и словари. Одноразовые `Client.StreamGuarded`/`Stream` используют ту же обязательную границу. Общей таблицы, новых полей запроса, заголовков или записей в БД нет.

Все допустимые окна форматированного PAN проверяются до 19 цифр, включая разные окончания при одном начале. Одинаковые spans удаляются как дубли; разные пересекающиеся валидные окна неоднозначны. Например, `3000 4111 1111 1111 1111` и `4111 1111 1111 1111 00` допускают несколько трактовок. Вместо выбора суммы слева/справа фильтр выдаёт отдельный preflight-сигнал `ErrInputAmbiguous` до reserve/ключа/POST. Пока есть старые пары истории и проверка бюджета ещё не вызывалась, Engine убирает старейшую пару только из текущего контекста и заново пропускает полный запрос через ту же сессию/фильтр. Сохранённая история не переписывается. Если неоднозначность находится в текущем вопросе или неудаляемой continuation, конечный результат — `MODEL_ERROR` с возвратом попытки без следующего POST; число повторов ограничено числом пар. Остальные ошибки фильтра этим сигналом не являются и остаются терминальными. Две непересекающиеся карты допустимы. Это ограничение простого фильтра, без каталога эмитентов или смыслового распознавания суммы.

Фильтр выполняет два прохода по полному запросу. Первый собирает реквизиты, распознанные по формату или метке. Второй заменяет точные известные значения в объявленных text/search полях, включая `filter.q` аргументов и `groups[].filters.q` результатов. Числовые границы проверяются. Финансовые поля не считаются текстом: даже protobuf int64 в строке `amount_minor`, численно равный PAN или телефону, остаётся точной суммой. Текстовые поля перечислены в `modelTextField`; при добавлении нового поля требуется определить его смысл.

Чтобы сохранить поиск по описанию, адаптер восстанавливает известный псевдоним в `filter.q` локальных `find_operations` и `aggregate_operations` перед обычной валидацией и выполнением. Например, модель возвращает `q: "[phone_<код>]"`, сервис ищет по исходному телефону. Другие аргументы и встроенный поиск не получают обратную подстановку. Преобразование не отвергает malformed соседние args раньше приоритетного `off_topic`: прежняя валидация и terminal priority остаются у Engine. Аргументы и их локальная raw-форма согласованы; следующий HTTP заново фильтруется.

Известные псевдонимы в `output_text` восстанавливаются локально до streaming callback/Engine.Append и в окончательных message text/Raw. Пользователь и БД видят исходную подпись; следующий вопрос фильтрует восстановленную пару вопрос/ответ одним новым псевдонимом. Неизвестные коды не меняются. Parser сначала сверяет исходный SSE с исходными text.done/part.done/final Raw; сравнение итогового текста Engine не ослаблено. Разрезанный между delta токен до завершения держит proper prefix (до 33 ASCII-байт) по output/content; очередь сохраняет порядок частей. Буфер и общий восстановленный текст ограничены существующим ResponseBytes. Flush привязан к проверенному text.done. Полные тексты и таблица соответствий не логируются.

Если bare номер был распознан только по метке, локальный `output_text` добавляет подпись «телефон …», «счёт …» или «карта …» перед дословным значением. Уже присутствующая метка («по карте …», «по телефону …») не дублируется: один formatter для delta и final Raw учитывает до 64 байт предыдущего текста каждой части. Цифры и исходное группирование не изменяются, `filter.q` получает точный оригинал. Уже самостоятельно распознаваемое оформление (например, `+7 …`) восстанавливается дословно. Это оформление реквизита, а не обещание неизменности любого текста. Оно необходимо, когда номер пришёл только из прошлого tool.description: сам старый результат инструмента не хранится в следующей истории, но подпись в восстановленном ответе позволяет снова распознать тот же raw номер и сохранить точный последующий поиск без таблицы соответствий в БД.

Исключение в оформлении — восстановленный форматированный PAN в `output_text` обрамляется видимыми «…»: `Карта «4111 1111 1111 1111» - 1000 ₽`. Дословный номер и сумма сохраняются; границы не позволяют следующему проходу по history/continuation склеить хвост карты и сумму в другое валидное окно. Общий formatter применяет эти границы в delta и final Raw с тем же бюджетом расширения. Локальный `filter.q` получает номер без добавленных кавычек.

Если перед известным alias уже есть открывающая « и сразу после alias (через не более 64 байт Unicode-пробелов) стоит закрывающая », formatter возвращает дословный номер без новой пары. Echo `« [alias] »` сохраняет одну пару. Streaming временно держит completed formatted alias + не более 64 байт пробелов в существующей bounded queue, пока не придёт первый значимый suffix или text.done; final Raw использует ту же проверку. При `«[alias] - 1000 ₽»` собственные границы нужны: результат `««номер» - 1000 ₽»` сохраняет и номер, и сумму; повторный echo этого оформления не добавляет слоёв. Окно считает байты (NBSP — два), ровно 64 допускаются, 65 — уже нет. Отсутствующее закрытие разрешается тем же formatter на text.done; новых таблиц/изменений q нет.

## История, старый контекст и внедрение

Каждый POST строит полный вход из хранимых пар, текущего вопроса и локальной continuation. `store:false`, `x-data-logging-enabled:false`, отсутствие conversation/previous_response_id сохраняются. Поэтому после включения фильтра старая история заново проходит правила, а прежний контекст у провайдера не используется для продолжения. Отдельного обновления или переписывания сохранённой истории не требуется. Видимый provider reasoning фильтруется вместе с остальным контекстом. Непустой encrypted_content завершает продолжение ошибкой без следующего HTTP. На mixed-version развёртывании старый экземпляр ещё может отправлять без фильтра: для включения защиты необходимо обновить все экземпляры, обслуживающие генерацию. Уже совершённые внешние передачи эта правка не отменяет и не удаляет.

Перед включением нужна публикация владельцем окончательного юридического пакета FIN-141 с новой версией и URL согласия помощнику. Новая `current_version` включается через существующую consent gate сервиса user: ранее выданное согласие на старую версию не должно пропускать запросы к модели. Затем все экземпляры generation должны работать с новым фильтром, а Android — показывать исправленное раскрытие ([отдельная часть FIN-366](https://github.com/fin-assist/android/pull/204)). Это порядок внедрения, а не подтверждение состоявшейся публикации/выкладки. Фиктивное изменение версии mock-согласия датой публикацию не заменяет; новых контрактных полей не требуется.

## Reasoning и совместимость поставщика

В [официальной схеме Responses API](https://aistudio.yandex.ru/en/docs/ai-studio/api/Responses/createResponse) ReasoningItem должен включаться в следующий ручной контекст. Поэтому видимые summary/content и сам item сохраняются и проходят рекурсивный фильтр. Непустой encrypted_content не является проверяемым текстом: даже при наличии видимого summary вся следующая отправка прекращается с MODEL_ERROR/refund. Пустое значение/отсутствие допускается. Фильтр не объявляет summary расшифровкой ciphertext и не повторяет запрос без обязательного контекста.

Нынешние двенадцать реальных recordings Alice AI LLM Flash не содержат output reasoning items; их успешный offline replay не доказывает совместимость encrypted reasoning. Поставщик/модель, требующие encrypted context, этим начальным фильтром не поддерживаются. Новых платных запросов для проверки не делалось; произвольные модели и этот режим совместимостью не объявляются.

## Границы результата

Суммы, даты, валюты, остатки, категории, банковские и торговые названия сохраняются. Вопросы про аптеку, лекарства и здоровье не блокируются по словам; встроенный поиск сохраняется с прежними инструкциями. Отдельного посредника веб-поиска нет; фильтр HTTP-входа не является доказательством состава внутреннего поискового запроса поставщика.

Правила не распознают универсально ФИО, адреса, паспорта, специальные категории сведений, переписанные словами/Unicode-цифрами реквизиты, нестандартное группирование, обфускацию, percent/base64-кодирование или произвольные вложенные форматы. Голые длинные числа без указанного контекста сознательно сохраняются, чтобы не повреждать финансовые значения. Возможны ложные срабатывания на финансовый текст, который совпал с явно обозначенным реквизитом или форматом карты с валидной суммой Луна. Имя в свободном описании или чувствительный факт может остаться в запросе. Результат уменьшает избыточную передачу; он не гарантирует обнаружение всех ПДн, юридическое обезличивание или соблюдение всех требований закона.

Документы в Confluence, Политика и согласие помощнику синхронизируются в FIN-366 по этим фактическим ограничениям. Текст документов не должен обещать удаление всех имён/чувствительных фактов. Фильтр сам по себе не меняет порядок получения согласий или правовые основания обработки.

## Проверки

`privacy_session_test.go` проверяет изоляцию сессий, дедупликацию и сохранение словаря через отказ бюджета/транспорта, сокращение истории и успешный второй POST; API повторяет матрицу PAN/phone/account с исходной историей PostgreSQL. `privacy_test.go` проверяет форматы, окна PAN, точность сумм/дат и quoted money, два прохода, копирование, вложенный JSON, предел глубины, отказ до HTTP/ключа/резерва и HMAC-корреляцию. `privacy_output_test.go` проверяет split-token carry, порядок частей, unknown alias, final Raw, ограничения расширения и ошибки callback. `privacy_http_integration_test.go` проверяет фактические HTTP-поля с соседними суммами/датами, известный q против равной quoted money и восстановление streaming текста с повторной маскировкой в follow-up. `privacy_integration_test.go` прогоняет Engine → HTTP → локальный поиск → второй HTTP. `client/privacy_test.go` проверяет проекцию без изменения originals и настоящий gRPC. `app/privacy_api_test.go` проверяет Ask/Watch/Retry на полной сборке с PostgreSQL18: каждый POST, второй проход по q, видимый ответ/историю, OFF_TOPIC над malformed соседним q со счётчиком/возвратом попытки, ошибки HTTP/фильтра. Живые запросы в Yandex не нужны.
