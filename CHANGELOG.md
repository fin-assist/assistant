# История изменений

## [Unreleased]

- FIN-225: contracts gen/go обновлён до v0.5.0. Ошибки результата одновременно содержат canonical `google.rpc.Status` и прежние поля потока/истории; сохранённый `retryable`, включая false и старые NULL-записи, сохраняет независимую семантику новой генерации. Usecase отмечает разрешение исходного RPC только на известных фазах отказа до эффекта; неизвестные исходы storage/COMMIT и replay без advice не получают положительного разрешения. Legacy-тексты остаются до обновления всех BFF и rollback-образов; выкладка и исправление специального phone replay в go-idempotency в этот PR не входят.

- FIN-347: библиотеки подняты вручную: go-grpc v0.1.0 → v0.2.0, go-postgres v0.2.0 → v0.3.0, go-idempotency v0.1.0 → v0.4.1 (Renovate-PR для assistant ни разу не открывался). debug-журнал вызова пишет отвергнутое значение `x-request-id` как `(rejected)`, а не как есть (FIN-300); смешанной модели доступа у assistant нет, поэтому FIN-299 допуск вызовов не меняет. Недоступный primary при живом контексте старта (в том числе молчащий с `connect_timeout`) — `ErrPoolUnavailable`, а не `context.DeadlineExceeded` (FIN-277). Источник миграций `idempotency` получает миграции 002–005 библиотеки (nullable `owner_id`, `resource_*` и индексы `CONCURRENTLY`); `migrate up` применяет их перед запуском новой версии; ключи, сохранённые прежней версией, воспроизводятся после обновления. Откат приложения: прежний бинарь работает со схемой версии 5 (новые столбцы nullable), но `migrate up` им не запускать — его источник `idempotency` знает только версию 1. Пример unit-файла стенда запускается при `ENV=stage`: `LoadCredential=stage-signing`, активные `AUTH_STAGE_SIGNING_KEY_FILE`/`AUTH_STAGE_PUBLIC_KEYS_FILE`, `SERVICE_NAME=assistant` в unit, режимы файлов ключей в шапке. Версии в `AGENTS.md`, README и `docs/` приведены к `go.mod`.
- FIN-324: `AUTH_MODE=verify` собирается вызовом `identity.NewAssembly` из `go-identity v0.2.0` вместо собственной сборки в `internal/app/identity.go`. Prod (ServiceAccount Kubernetes и JWT пользователя) проверяет токены как прежде; добавлен stage-режим `ENV=stage` с файлами ключей `AUTH_STAGE_ISSUER`, `AUTH_STAGE_SIGNING_KEY_FILE`, `AUTH_STAGE_PUBLIC_KEYS_FILE` (в prod запрещены). `verify` при `ENV=dev` теперь ошибка конфигурации. Обновление ключей — фоновое задание `identity-keys`; новая метрика `finassist_identity_jwks_skipped_keys{source}`.
- FIN-289: во время `SHUTDOWN_DELAY` HTTP `/readyz` отвечает 503 вместе с gRPC health `NOT_SERVING` (раньше до конца паузы — 200), после `Drain` цикл готовности не может снова сообщить готовность; `DB_MAX_CONNS` вне диапазона int32 — ошибка конфигурации, а не молча усечённое значение. Проверка `insecure-dev` вне `ENV=dev` в сборке уже была.
- FIN-290: `make test-names` проверяет и fuzz-цели (`FuzzUnit…`/`FuzzIntegration…`/`FuzzAPI…`, seed-корпус — в своём наборе) и отклоняет `Example…`, которые выполнялись бы вне трёх наборов покрытия.
- FIN-326: устранена нестабильность `TestAPIDialogueAPIWatchListenerDisconnectAndRecovery`: тест ждёт завершения прерванного backend PostgreSQL, а не проверяет `pg_stat_activity` сразу после разрыва.
- FIN-302: AskQuestion отклоняет текст из одних пробельных символов (`VALIDATION_ERROR`, `REQUIRED`) и текст с NUL (`INVALID_FORMAT`) до ключа, согласия и списания. Раньше NUL давал `INTERNAL`, а пустой текст — неустранимый `MODEL_ERROR`.
- FIN-298: порядок проверок AskQuestion/RetryAnswer приведён к grpc-api.md 5.2 и 7.4. Блокировка OFF_TOPIC (429) проверяется до запроса согласия в `user` и повторно под блокировкой пользователя; у RetryAnswer чужой или несуществующий ответ даёт `NOT_FOUND` до `CONSENT_REQUIRED`/`LIMIT_EXCEEDED`. Схема и контракт не меняются.
- FIN-305: чтение истории для контекста модели ограничено `LIMIT` по числу пар: сценарий передаёт в `History` наибольшее число пар, которое окно истории может вместить при бюджете `ASSISTANT_HISTORY_TOKENS` (`(токены×4 − 1) / 65`, 984 при 16000). Раньше запрос вычислял и передавал все завершённые пары пользователя. Отсечение по байтам по-прежнему в Go, состав контекста не меняется; схема и индексы не меняются.
- FIN-304: у каждой функции модели (`get_data_overview`, `aggregate_operations`, `find_operations`, `get_analytics`, `list_periods`, `present_result`, `cannot_answer`) своё короткое описание вместо общего: что возвращает и когда вызывать. У полей схем — описания: суммы в минимальных единицах валюты, `from`/`to` — RFC 3339 со смещением пояса пользователя на эту дату, полуинтервал `[from, to)`, `result_id` — `call_id` предыдущего чтения. Размер схем всех функций в запросе — 4672 → 6462 байта (около +450 расчётных токенов на шаг). Разбор аргументов и поведение функций не изменены.
- FIN-256: общие server/client/reqctx подключены из `go-grpc v0.1.0`, миграции и тестовый harness — из опубликованного `go-migrate v0.1.1` с исправлением library up/down/up (FIN-262), фоновые циклы — из `go-worker v0.1.0`, lifecycle пулов — из `go-postgres v0.2.0`. Добавлены HTTP/SSE integration-проверки повреждённого lifecycle и отказов провайдера: без terminal output/tool calls, утечки ошибок и повторного POST. Удалены локальные копии инфраструктуры; сохранены streaming, identity, read-primary, транзакции, idempotency, диалог и режим без модели.

### Изменено

- FIN-240: управление транзакциями перенесено на `go-postgres v0.1.1`: общий менеджер для запросов и COMMIT, отказ от контекста чужого менеджера без записи вне транзакции. Пулы primary/replica и атомарность idempotency/tombstone сохранены. Чтение диалога использует `RunWith`: отдельно — primary REPEATABLE READ READ ONLY, внутри своей транзакции — её снимок и опции. Новых ошибок контракта и изменений схемы нет.
